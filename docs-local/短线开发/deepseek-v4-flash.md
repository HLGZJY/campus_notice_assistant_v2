## Q2 考量维度排序

**结论：学习价值 > 时间预算 > 维护复杂度 > 用户价值 > 技术可行性 > 成本**

1. **学习价值**（最高）：项目的收益函数是方法论迁移，不是产品成功。决策标准应是"这件事教会我什么不能从教程里学到的"——检索评测、成本工程、harness 属于此类；多角色页面、Docker 不属于。
2. **时间预算**：在校生每周 15-20h 是硬约束，一切 scope 由它门控：任何超过 1 周的事拆或砍。
3. **维护复杂度**：单人开发 = 每多一个需要维护的东西都在借未来的时间。你现在的文档体系（372 行待确认 + 审计表）已经是真实的维护负担。
4. **用户价值**：重要但不是最优先——系统跑稳、10 个人用上一周之前，"用户价值"是假想。
5. **技术可行性**：MVP 已去掉 80% 的风险；剩余的是网站改版、API 波动这类"可观测风险"，不是"需提前确认的风险"。
6. **成本**：绝对值极小（每月几十元内），但"计量缺失"比"价格高"危险——它排最后不代表不管它。

## Q3 阶段2 前必须确认的 6 个决策点（给方法，不给名字）

**结论：阶段2 的投入隐含 4 个未经证实的故事，每个都需要信号而非观点。**

1. **用户是否真需要"一键下单"**（最重要）
   方法：现 UI 加一个"服务市场"页，按钮是假的（点击记录 + 弹"演示版"提示），用一周。
   信号：服务按钮点击 ≥ 待办浏览量的 30%，或 ≥3 人主动问"怎么真的能下单"。达不到 → 阶段2 砍掉服务市场。
2. **采集管道能否长期稳定**
   方法：W1 后连续跑 2-4 周，记录抓取/提取/重试/token 四类指标，每周人工抽查 10 条。
   信号：抓取成功率 ≥90%、提取失败率 <10%。所有推送类功能以此为前置。
3. **批量生成待办 vs 按需生成**（你决策 3 的实证）
   方法：先跑两周按需，统计"用户实际点开生成的次数"和"标记无用的比例"，再对比批量模拟成本。
   信号：27 条通知里点开生成 <5 次 → 批量生成是在为一个没人用的功能付钱，维持按需。
4. **混合检索值不值得上**
   方法：用 W2 的 20 题测试集对比 纯向量 vs BM25+RRF。
   信号：MRR/Rec@k 提升 ≥10% 且无回归才上。110 个 chunk 大概率测不出差异——测不出就不上。
5. **模型分工要不要升级**
   方法：执行 issue #2（同 prompt/同数据/同温度，黄金集对比 + token 成本）。
   信号：便宜模型准确率 ≥ 当前 -5% 且成本低一半 → 换。
6. **多用户是不是真实需求**
   方法：W4 后看单用户版使用数据。
   信号：连续 2 周 ≥3 个真实用户主动使用，或出现明确部署场景（导师/班级）。否则阶段2 的多用户是虚构需求。

## Q4 技术选型为什么

**结论：整体选型合理。明确反对一条：决策 3 的"批量生成待办"（见第 7 项）。**

**OpenAI Agents SDK**

- 核心理由：`output_type` 受约束输出是结构化提取的地基；tool 注册 + 按 Agent 分组成本最低；第三方兼容接口保供应商可换。
- 最可能失败：阶段2 你要自定义 harness 层（循环检测、审批联动、SSE 可视化）时，SDK 封装会挡路。
- 何时换：挡路且绕不过时，退回 `utils/llm.py` 裸调用 + 手写 Pydantic 校验（你已有，成本极低）。不建议换 LangGraph。

**SQLite → PostgreSQL**

- 核心理由：单机单进程零运维；27 条数据规模性能绰绰有余。
- 最可能失败：太早迁移——阶段2 之前迁移纯属浪费学习预算。
- 何时换：真实多用户并发写或上云时。SQLite WAL 可再撑一阶段；走 SQLAlchemy 迁移成本低，"晚换"无代价。

**Chroma**

- 核心理由：本地 CPU 可跑；增量 add 已实现；元数据过滤够用。
- 最可能失败：chunk 到 10 万级的内存与查询；混合检索需外部 BM25 配合（`rank_bm25` 即可，当前规模无压力）。
- 何时换：多用户阶段换 pgvector（随 PostgreSQL 顺路）或 Qdrant。现在不换。

**本地 embedding（all-MiniLM-L6-v2）**

- 核心理由：零成本、离线、快；MVP 够用。
- 最可能失败：中文语义质量——专有名词/课程名召回差，这是 W2 评测最可能暴露的问题。
- 何时换：评测证明检索层是瓶颈且 BM25 补不上时，换 bge-small-zh-v1.5（本地 CPU 可跑）。没数据前不换。

**Streamlit（阶段2 换什么）**

- 核心理由：迭代最快；"Agent 仪表盘"定位已被你的需求文档确认。
- 最可能失败：阶段2 要 SSE 过程可视化 + 审批门控 + 多角色页面时，回调模式变面条代码。
- 何时换：阶段2 前端重做时。替代：**FastAPI + HTMX/轻量 JS**（单人最优：无 Node 构建链、SSE 原生支持）；Next.js 需投入前端学习预算，性价比低。FastAPI 本身也是后端背景的必修课。

**newspaper4k**

- 核心理由：中文提取开箱即用，M1 三个栏目已实测。
- 最可能失败：学校网站改版/非标准结构 → 静默失败；JS 动态渲染页抓不到。
- 何时换：具体栏目失效时写 requests+bs4 fallback（可控、可加重试与指纹）。别为"将来"重写。

**批量 LLM 处理（反对你的决策 3）**

- 支持的部分：增量只处理新通知、并发限流、指数退避——全对，必须保留。
- 反对的部分：当前规模（27 条、1 条有效待办）下"采集时批量生成"收益为零——周成本差是几毛钱，而噪声待办污染界面、数据源开关配置复杂度是真实的。
- 建议：维持 M3 的按需生成现状，`batch_generate()` 留作后门，等通知量到百级、待办命中率有数据支撑再翻转。

## Q5 额外问题

**a. 里程碑式验收**

- **M-自运行**：连续 7 天无人干预跑通"抓取→提取→索引→待办"；任意一天崩溃后重启可续跑、不重复计费；抓取成功率 ≥90%。
- **M-有用性**：10 人用 1 周，≥3 人说"每天会打开"；待办被标记完成 ≥20 次；20 题人工问答评分 ≥4/5。
- **M-闭环**：通知→待办→提醒→（可选下单）全链路可演示；幂等与三层审批有自动化测试；重复点击不产生双订单。
- **M-学习**（最易漏但最重要）：不看文档能向别人讲清——RAG 三层评估怎么做、token 成本模型怎么算、为什么这个系统不需要多 Agent。

**b. 最大失败风险（反对者视角，4 个真实坑）**

1. **文档工程陷阱**：待确认文档 372 行 + 需求文档 210 行 + 审计表——架构确认本身正在消耗学习预算。判据：连续 2 周文档行数 > 代码行数 = 方向错了。
2. **价值假设未验证就进阶段2**：一键下单是重投入（订单状态机、审批、服务商对接），却建立在"用户会下单"这个未验证故事上。你目前唯一被验证的痛点是"错过截止时间"。
3. **小数据上的过度优化**：27 条通知、110 个 chunk 上谈混合检索和评测体系，统计上全是噪声——你现在测出的任何"改进"都可能不可复现。
4. **成本无声失控**：批量提取 × 多学校 × 长正文，一轮 50K token，每天多轮 = 每月数百元；没有计量表你永远不知道涨在哪。重试率是放大器：提取失败 → 重试 → 双倍成本。

**c. 未来 4 周只做一件事**：W1 的定时调度 + 增量管道自运行。

理由：它是提醒/推送/评测/多用户一切的地基；学习价值最高（幂等、断点、可观测是所有 AI 系统的通用能力）；它产生真实数据（失败率/token/重试率），这些数据是所有阶段2 决策的输入。没有"活着的系统"，其他功能都是在给尸体化妆。

**d. 最容易过度设计的环节**：**评测体系**（LLM-as-Judge、κ>0.6、RAGAs 三层、交换增强）。你单人标注，κ 一致性校验根本不成立；27 条数据上 MRR 波动 ±30% 是常态。你的评测就应该是：20 条问题 + 你自己打分 + 对比表。次之：混合检索（110 chunk）；再次：批量待办生成。

**e. 最值得学透、可迁移的 3 个技术点**

1. **受约束输出 + 校验重试循环**（Pydantic output_type + 错误回传重试）：所有 LLM 生产应用的地基。M2 已做对，补学"错误设计"层面——什么错误值得重试、上限几次。
2. **RAG 评测方法论**（检索→生成→端到端三层 + 错误归因）："能证明 RAG 变好"是与只会调库的人拉开差距的能力，迁移性最强。
3. **成本驱动的管道工程**（增量处理、token 计量、并发限流、指数退避）：LLM 应用的工程经济学，预算约束下的生存技能。
   （第 4 名备选：Prompt 链 vs Agent 的边界判断——你决策 1 已证明判断力，保持即可。）

## Q6 三条独立建议

1. **先让系统"活着"，再让它"聪明"。** 未来 4 周的目标不是新功能，是让它在无人干预下连续跑 2 周。运行数据（失败率/token/重试率）比任何架构审计都更早告诉你阶段2 该做什么。
2. **停止"确认"，开始"证伪"。** 待确认文档里 90% 的条目，答案已经写在你的代码里；与其逐条确认，不如给 10 个同学用一周——两种做法得到的信号质量完全不同。
3. **阶段2 的蓝图要砍 80%。** FastAPI + PostgreSQL + 队列 + 服务市场 + 多角色不是"下一个阶段"，是 3-6 个月的全职工作量。最可能的真实路径是：把"通知 + 待办 + 提醒 + 订阅"做成每天被使用的单用户工具，服务市场等用户密度出现再说。提醒（错过截止）是你已验证的痛点，一键下单不是。
