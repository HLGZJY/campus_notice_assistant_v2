# 短线开发定稿(4 周)

> 来源:综合 `deepseek-v4-flash.md`(主线)与 `deepseek后续规划建议.md`(技术点)。
> 约束:15-20h/周;目标:做成真能被同学用的工具;4 周内单用户自用验证,阶段2 做 APK(不上架)。

## 考量维度排序

学习价值 > 技术可行性 > 可调试性 > 时间预算

- 可调试性为硬约束:AI 报错是"文不对题",后端报错有堆栈。日志/中间结果写入时间 ≥30%。
- 维护复杂度、用户价值、成本隐含在技术可行性之后,不单独排序。

## 4 周计划

| 周 | 内容 | 验收信号 |
| --- | --- | --- |
| W1 | 主线:定时调度+增量闭环——APScheduler 独立进程(不塞进 Streamlit)、内容指纹变更检测、断点续跑(status 游标)、token 计量表;日志/中间结果 ≥30% 时间。并行支线:Tool Calling 循环——注册假工具、强制 Max 5 轮守卫、每轮打印 tool_calls 日志 | 连续 7 天无人干预运行;崩溃重启可续跑且不重复计费;每轮 tool_calls 可日志回放;LLM 遇"服务不可用"不瞎编 |
| W2 | 检索质量基线:20 题测试集(含 5 条过期陷阱题 + RAG 污染专项:删通知后 Chroma 幽灵结果);先纯向量基线,再过期降权/排除对比,追加 RRF+BM25(rank_bm25,k=60)对比 | 改进前后对比表(负结果也有效);混合检索 Top5 召回 >0.75 且超纯向量基线 10%;污染用例有明确处理策略 |
| W3 | 主动提醒+关键词订阅:截止前 3/1 天提醒(站内红点)、订阅词匹配推送;Streamlit 用两步式交互(短周期不换前端) | 演示"通知发布 → 订阅用户收到提醒"全链路;提醒不依赖死系统 |
| W4 | 单用户深度自用 + 埋点(页面点击、问答次数、待办标记、服务按钮点击),跑 7 天自运行终检 | M-自运行达标;自用数据落盘;至少 3 条"证据支持的下一步"作为阶段2 输入 |

## 技术选型(现 MVP 保持,触发条件才换)

| 技术 | 保持理由 | 换的条件 |
| --- | --- | --- |
| OpenAI Agents SDK | output_type 受约束输出;tool 注册成本低 | 自定义 harness 层挡路时退回 utils/llm.py 裸调用 + 手写 Pydantic 校验 |
| SQLite(WAL) | 单机零运维,当前规模绰绰有余 | 第一次出现并发写锁报错时,换 PostgreSQL/Supabase |
| Chroma | 本地 CPU;增量 add;元数据过滤够用 | delete ID 映射混乱/幽灵结果(即 W2 专项)处理不了,换 Qdrant |
| all-MiniLM-L6-v2 | 零成本离线快 | 评测证明检索层是瓶颈且 BM25 补不上,换 bge-small-zh-v1.5 |
| Streamlit | 4 周内迭代最快;两步式交互绕过状态问题 | 阶段2 重做前端时换 FastAPI + HTMX |
| newspaper4k | 中文提取开箱即用,M1 三个栏目已实测 | 具体栏目失效时写 requests+bs4 fallback;JS 动态页用 Playwright(按需) |
| 批量 LLM 生成 | 反对。27 条规模收益为零,噪声污染界面 | 通知量到百级且有数据支撑再考虑 batch_generate() 后门 |

## 阶段2 前端与 APP(定方向,4 周内不碰)

- 前端:FastAPI + HTMX 替换 Streamlit(SSE 原生支持、无 Node 构建链;FastAPI 也是后端必修课)。
- APP:同一套 FastAPI 后端 + 移动端 WebView 壳打包 APK(Capacitor/WebViewAPK),不上架,仅打安装包;响应式移动优先 UI 保证体验。APK 推送等 WebView 能力单独验证。
- 备选(不预支):若试装反馈差再评估原生 Flutter/Compose,属 3-6 个月量级。

## 里程碑

- **M-自运行**(4 周内):连续 7 天无人干预跑通"抓取→提取→索引→待办";崩溃重启可续跑、不重复计费;抓取成功率 ≥90%。
- **M-检索线**(W2 末):Top5 召回 >0.75 且超纯向量基线 10%;改进前后对比表。
- **M-闭环**(W3 末):通知→待办→提醒→订阅全链路可演示;幂等有自动化测试。
- **M-有用性**(推迟至阶段2):随 APK 试装,10 人用 1 周,≥3 人说"每天会打开"。
- **M-学习**(贯穿):不看文档能讲清——RAG 三层评估、token 成本模型、为什么这个系统不需要多 Agent。

## 无脑采纳项(成本极低)

1. 手册式 system prompt:操作手册风格,含"歧义必反问""引用带标题""禁止推测未提供的日期"。
2. 代码分目录:`src/deterministic/`(爬虫、SQL、规则)与 `src/stochastic/`(LLM 调用、prompt),LLM 代码不直接调 SQL。
3. 30% 时间写日志:print()/JSON 中间结果/回放工具,调试 Agent 的硬功夫。
4. 停止"确认",开始"证伪":待确认文档 90% 条目答案已在代码里,让数据说话。

## 失败风险清单(反对者视角)

1. 文档工程陷阱:连续 2 周文档行数 > 代码行数 = 方向错了。
2. 工具循环死锁:无 tool_call_id 去重,反复调同一工具——缓存上次 tool 输出并告知 LLM。
3. RAG 污染:删了过期通知但 Chroma 没删 → W2 专项处理(降权/排除/删除策略)。
4. 成本无声失控:批量提取 × 多学校 × 长正文,无计量表永远不知道涨在哪;重试率是放大器。
5. 评估靠感觉:黄金集过拟合,新数据可能掉到 60%,W2 起建立持续评估习惯。

## 最值得学透、可迁移的 3 个技术点

1. 受约束输出 + 校验重试循环(Pydantic output_type + 错误回传重试):所有 LLM 生产应用的地基。
2. RAG 评测方法论(检索→生成→端到端三层 + 错误归因):"能证明 RAG 变好"是与只会调库的人拉开差距的能力。
3. 成本驱动的管道工程(增量处理、token 计量、并发限流、指数退避):LLM 应用的工程经济学。
