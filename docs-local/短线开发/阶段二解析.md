基于这份《短线开发完整计划》，后续（4周内）要做的**核心工作**是：将现有的**“手动触发、被动问答”的 MVP 原型**，升级为**“自动运行、主动提醒、可评测、可观测”的单用户自用系统**。

说白了，**原有功能（抓取、提取、RAG问答）基本不动，这4周全是在“外围”和“基建”上做工程加固和数据验证**。

以下是**新增内容的清晰分类清单**：

### 1. 基础设施与可观测性（让系统“活”起来且可被监控）

原有系统需要手动跑脚本，现在给它装上“大脑”和“仪表盘”：

- **独立定时调度器**：新增 `scheduler.py` 进程，让系统按 `config/app.yaml` 的间隔自动抓取、自动提取，无需人工干预。
- **断点续跑（幂等性）**：新增 `status` 游标机制。系统崩溃重启后，能接着处理未完成的通知，**已完成的绝对不会再调 LLM 扣费**。
- **Token 计量表**：新增 `token_usage` 数据库表。在 `utils/llm.py` 统一埋点，记录每次提取/待办/问答消耗的 token，并在系统配置页新增“近7天用量”看板。
- **内容变更检测（指纹）**：`notices` 表新增 `content_hash`（正文哈希）。爬虫再次抓取同一 URL 时，只更新正文变化的通知，不再全量重跑。

### 2. 检索质量工程（RAG 的“质检”与“优化”）

原有 RAG 是“黑盒”，现在引入评测驱动开发：

- **20题测试集**：新增标准 JSON 测试集（含常规语义、专有名词、过期陷阱等题型），用于量化召回能力。
- **基线评测脚本**：新增脚本对 Chroma 纯向量检索跑分（Top5 召回率、MRR），按题型暴露短板。
- **过期过滤策略**：新增三档实验（不过滤 / 降权 / 排除），解决“问最近通知却返回过期内容”的问题。
- **混合检索（BM25 + RRF）**：新增 `rank_bm25` 检索器，与向量结果做倒数排名融合（RRF），看是否能提升召回率（不达标则不上线）。
- **RAG 污染防护**：新增一致性校验脚本，确保删除 SQLite 通知时，Chroma 中的残留向量能被同步清理，杜绝“幽灵回复”。

### 3. 主动服务能力（从“你问他答”变成“主动推送”）

原系统只能被动等待用户查待办，现在新增业务闭环：

- **关键词订阅（规则引擎）**：新增订阅表和管理页。支持用户添加订阅词，抓取到新通知时**用确定性匹配（子串，不用LLM）**自动标记命中。
- **截止日期提醒**：新增提醒表和定时扫描任务。对截止前 3 天/1 天的通知/待办，**幂等地**生成提醒；首页新增红点，待办中心新增提醒区（已读/忽略）。
- **两步式交互**：针对订阅保存、提醒忽略等操作，改为“预览 → 确认”两步，规避 Streamlit 长时状态导致的卡顿。

### 4. 产品验证与数据决策层（为“要不要做下一阶段”铺路）

这些完全是新增的“埋点”和“终检”模块，用于收集真实使用证据：

- **用户行为埋点**：新增事件表，记录页面访问、问答次数、待办生成点击、**“假服务按钮”点击（用于验证是否有复购/下单意愿）**。
- **7天自运行终检**：新增每日体检脚本，连续 7 天无人干预运行，监控抓取成功率（≥90%）、提取失败率（<10%）、Token 消耗，并做一次真实的崩溃恢复演练。
- **门控数据采集**：对照定稿中的 6 大技术门控（如混合检索要不要上、便宜模型能不能换、多用户值不值得做），**全部用这4周跑出的实测数据（对比表、埋点转化率）来回答，不再凭感觉决策**。

---

**一句话总结：**
这4周**没有给核心业务（提取/问答）增加任何新的复杂 AI 功能**，纯粹是在做**工程确定性（调度/幂等/计量）、质量可测性（评测集/对比实验）和产品验证性（提醒/埋点/终检）**——即把“能跑的通路”变成“跑得稳、测得准、有数据支撑下一步决策”的系统。
