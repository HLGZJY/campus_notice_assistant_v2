**b. 最大的 3 个失败风险（扮演反对者）**

1.  **“工具循环死锁”**：LLM 调工具拿不到数据，回头又说“让我再试试另一个参数”，结果反复调同一工具，轮数耗尽。你目前的代码没有 `tool_call_id` 去重，**第 2 周必现**。解决方案：必须缓存上一次 tool 输出，告诉 LLM“你已经查过了，结果一样，换别的办法”。
2.  **“RAG 污染”**：当你删除了过期的竞赛通知，但 Chroma 没删，用户问“最近有什么比赛”，LLM 会引用过期的比赛，诱导用户去报名已截止的活动。**这对用户是真实的伤害（浪费感情）**。你的 Q2-3 说“降权或排除”，但没写代码，这个坑你一定会踩。
3.  **“评估靠感觉”**：你黄金集 100% 是严重过拟合（就那 6 条）。新的 50 条通知到来时，准确率可能掉到 60%。你没做“持续评估”的 pipeline，一旦准确率崩了，你不知道是 prompt 问题、分块问题还是模型问题。

**c. 未来 4 周只能做一件事：**

**做“带防幻觉机制的 Tool Calling 循环”**。理由：这是 AI 应用区别于传统后端的最核心能力，学通了可迁移至任何 Agent 项目（客服、销售、数据分析）。RAG 调参是体力活，后端 CRUD 是搬砖，只有 Tool Calling + 状态管理是“AI 工程”的灵魂。

**d. 哪个环节最容易过度设计？**

**“服务调度 Agent / 多服务商匹配”**。你现在的阶段根本不需要“智能分发”，只需要一个 `if service_type == 'print'` 硬编码。你列出的“订单智能分发 Agent”“流量统计 Agent”纯属脑补——没有真实服务商接入，这些全是空中楼阁。**强烈建议砍掉所有“调度/分发”相关的 class 设计，全部用函数硬编码，直到你真有第二个服务商接入。**

**e. 最值得学透、可迁移的 3 个技术点**

1.  **结构化输出（Pydantic + LLM）**：学会 `output_type` 校验 + 重试回传错误信息。这是所有 AI 数据管道的基础。
2.  **检索排名融合（RRF）**：理解“稀疏（BM25）+ 稠密（向量）”为什么是工业界标配，这比单纯调 embedding 模型重要得多。
3.  **Agent 循环的“可中断性”**：学会在 `while round < max` 里插入 `yield` 或日志检查点，让 Agent 不是黑盒，而是可步进调试的。
