### Q1. 理想终态架构（推翻与升级）

**结论：** 你现有的架构方向 80% 是正确的（尤其是 Prompt 链 + ReAct 的定位），但在存储、前端、Embedding 三个层面，理想情况下需要**彻底推翻**。此外，“非多 Agent”决策在服务调度环节需要**松动**。

**理想全景图（组件级）**：

1. **接入层**：Nginx + FastAPI（UVicorn）。
2. **展示层**：**Next.js (React) + Tailwind**（面向用户） + **Streamlit**（保留给内部管理/调试仪表盘，不面向生产用户）。
3. **核心编排层（关键升级）**：
   - **Orchestrator (Router)**：识别意图（查通知 / 办事务 / 闲聊）。
   - **P&E Pipeline**：采集→提取→标准化（确定性+LLM，保持不变）。
   - **ReAct Worker**：处理工具调用。但这里不再是单一的 ReAct，而是引入 **“Plan-and-Execute”**（先规划步骤，再执行工具），因为下单、组队是多步操作。
4. **数据层（大换血）**：
   - 主库：**PostgreSQL**（替代 SQLite）。
   - 向量库：**pgvector**（彻底替代 Chroma）。
   - 缓存：**Redis**（会话状态 + 限流 + 分布式锁）。
   - 对象存储：**MinIO / OSS**（存抓取的原始 HTML/PDF，而非只存文本）。
5. **协议**：MCP **需要**（在阶段3对接外部服务商时），A2A **不需要**（因为你是一家独大的中心化系统，无需 Agent 间互操作）。

**我的明确反对意见（现有决策需推翻的）**：

- **Streamlit 够吗？** **不够。** 理想生产环境下，Streamlit 的细粒度 UI 控制差、状态管理混乱、SEO 为零。必须用传统前后端分离（Next/React）做用户端，Streamlit 只做你的“内部 AI 调试控制台”。
- **Chroma 换 pgvector 吗？** **必须换。** 除非你永远单机。多用户、多学校、权限隔离（RBAC），pgvector 的行级安全策略（RLS）是 Chroma 永远做不到的。`metadata filtering` 在 Chroma 里是玩具级，在 PG 里是标准 SQL。
- **本地 Embedding（all-MiniLM）换 API 吗？** **必须换。** 理想蓝图下，时间无限、算力可扩展，但**人力有限**。本地 Embedding 需要你自己维护模型加载、推理优化和版本更新。API 模型（如 `text-embedding-3-small` 或 `voyage-2`）的检索准确率（MTEB）比 all-MiniLM 高 10%~15%，且成本极低。省下的心力用来优化 RAG 分块和重排序。
- **“采集时批量生成待办”** **需要松动为“缓存无效化”模式**：单用户时可行；多用户/多学校时，每个学校/学院的通知对不同用户（本科生 vs 研究生）生成的待办不同。在采集时全部预生成会造成算力爆炸。应改为“读取时按需生成 + Redis 缓存（带 TTL）”。

### Q3. 阶段排序逻辑：为什么是这个顺序？

- **阶段 1 & 2（数据底座+RAG内核）不可跳过**：这是**地基**。如果你先做前端（阶段4）或工具（阶段5），会发现向量不准、权限混乱，全部返工。**先搞定数据质量，再搞业务闭环**。
- **阶段 3（身份）可以并行于阶段 2**：如果你对 SQL 熟练，可以边改向量边加 RLS，但我不建议新人并行。
- **阶段 4（前端解耦）是“痛苦但正确”的**：它可以放在阶段 5 之后，但越晚，Streamlit 里积累的 UI 逻辑迁移成本越高。建议在阶段 3 完成后立即动手。
- **阶段 6（MCP）是可选加分项**：如果你只想做校内单体，直接用 FastAPI 暴露接口给打印店老板看后台页面即可，**MCP 并不是必需品**。只在你有 3 家以上外部服务商需要标准化接入时才引入。

### Q4. 需要确认什么（关键决策点与验证方法）

1. **多租户模型确认（阶段1前）**：
   - 问题：学校 A 的通知是否要隔离？学生能否跨学校查看？
   - 验证方法：画出 ER 图，明确 `tenant` 是“学校”还是“学院”。
   - 信号：PostgreSQL 中的 `notices` 表是否有 `tenant_id` 且不可为空。

2. **“待办”的生成时机确认（阶段5前）**：
   - 问题：到底是在采集时生成（旧决策）还是读取时生成（建议升级）？
   - 验证方法：模拟 1000 条通知 × 3 个角色（本科生/研究生/教师）。采集时生成 = 3000 条待办；读取时生成 = 0 条预生成，仅缓存命中。
   - 信号：**如果缓存命中率 > 80%，选择读取时生成**。这是成本与性能的黄金分割点。

3. **LLM 工具调用幻觉边界（阶段5前）**：
   - 问题：LLM 读取用户指令“帮我报个名”时，如果找不到对应通知，是否允许它编造链接？
   - 验证方法：设置“强制接地”规则——工具调用的 `notice_id` 必须来自上一轮 RAG 检索返回的 ID 列表，否则拒绝执行。
   - 信号：编写针对“不存在通知”的测试用例，LLM 必须返回“未找到，请提供链接”而不是瞎编。

### Q5. 技术选型深度解析（核心理由与替代方案）

| 技术 | 核心理由（≤3条） | 最可能失败的场景 | 替代方案 | 何时该换掉 |

| **Streamlit→Next.js** | 1. 生产级 UI 控制。2. 流式响应（SSE）更稳定。3. 移动端适配。 | 开发周期拉长 3 倍；后端需要提供 RESTful 接口。 | **Gradio**（比 Streamlit 灵活一点，但本质相同）。 | **阶段4 必须换**，否则你永远在“玩具”层面。 |

### Q6. 额外问题（犀利的自我审视）

**a. 项目“做完”的验收标准（里程碑式）**：
- **Phase 1（数据）验收**：新增 1 个新学校网站，仅改 YAML 配置即可跑通，无需改代码。
- **Phase 2（检索）验收**：在 100 条标注问答上，`Answer Recall@3`（答案出现在 Top3 片段中）≥ 90%。
- **Phase 3（事务）验收**：从看到通知到生成有效订单，**用户操作步骤 ≤ 3 步**（点击待办→确认信息→下单）。
- **终态验收**：连续运行 1 个月，**零人工干预**，抓取成功率 > 99%。

**b. 最大的 3 个失败风险（反对者视角）**：
1.  **网站结构变动（爬虫崩塌）**：这是最致命的。学校官网改版一次，你的整个 pipeline 废掉 50%。**坑**：你会上线 80% 的时间都在修 XPath，而不是写 AI。
2.  **“虚假闭环”陷阱**：你费劲接入了文印店 API，但学生其实更喜欢直接去店里打印。**需求不存在**。阶段5 投入巨大，但无人使用。
3.  **向量污染**：当你批量重跑提取时，pgvector 里的旧向量没删干净，导致问答引用到“已下架”的旧通知。这会彻底摧毁用户信任。

**c. 最不可跳过、先做透的阶段**：
**阶段 2（混合检索与 RAG 2.0）**。
理由：AI 校园助手的核心价值只有“**找得准**”和“**答得对**”。工具下单是锦上添花，检索不准是雪崩。如果把所有时间砸在 RAG 评估和重排序调优上，这个项目已经成功了 70%。

**d. 最容易过度设计的部分**：
**MCP 协议集成（阶段6）**。
你的决策清单里写了“阶段3引入 MCP”。但在只有 1 个打印店、2 个跑腿团队时，写一个 Restful API 给店家配个后台管理页面，比实现 MCP Server 简单 10 倍。**过度设计指数：⭐⭐⭐⭐⭐**。仅在标准化接入 > 3 家异质服务商时引入 MCP。

**e. 最值得学透、可迁移的 3 个技术点**：
1.  **RAG 评估方法论（Golden Set + Hit Rate + MRR）**：这是所有 AI 应用（客服、文档搜索）的通用骨架。
2.  **Human-in-the-loop 工具调用（审批门控）**：这是所有企业级 AI（金融、医疗）落地的硬门槛，学会了可以横着走。
3.  **向量与结构化数据的混合查询（SQL+Vector）**：这比纯向量检索或纯 SQL 都要难，但这是任何“智能数据库”的标配能力。

### Q7. 作为架构师，给你的 3 条“你可能没意识到”的话

1.  **“无限时间”的敌人不是复杂度，是“维护倦怠”**。
    现实是，理想蓝图有 8 个阶段，当你做到阶段 4 时，阶段 1 抓取的网站改版了。你必须在每个阶段结束时，**强制写“监控活页”**（即：如果这个模块明天坏了，我怎么在 5 分钟内发现？）。没有可观测性的蓝图，是纸上谈兵。

2.  **你最大的优势不是后端，是“场景贴身”**。
    不要闭门造车。即使只有你一个用户，也请打开电脑，**每天真实使用自己的工具**去查看学校通知。你自己觉得“别扭”的地方（比如待办卡片太长、问答回复太慢），就是第二阶段最该优化的地方。工程师自用是消灭伪需求最锋利的刀。

3.  **LLM 只做“理解”，不做“决策”**。
    你的决策清单里提到“个性化推荐用 LLM 精排”，我强烈反对在 MVP-Plus 阶段使用。LLM 做精排会引入随机性（同一用户刷新两次，推荐不同）。用**规则粗排（时间衰减+类型权重）** + **确定性 SQL 排序**，先把产品逻辑跑硬，再用 LLM 微调权重。**硬逻辑是骨架，LLM 是血肉，别搞反了**。
