**Q1. 理想终态架构**

**结论。**  
理想产品是一个多租户、多学校的校园操作系统，将每一条官方通知转化为共享、可版本化、可执行的工作项，再在明确的人机协同门控下，将用户路由至正确的校内履约渠道。系统刻意**不是**自由形态的多智能体社会。持久骨干是确定性数据管道（采集 → 提取 → 物化待办 → 索引），外加薄路由层与单一 ReAct 风格对话智能体。其余全部为确定性代码、规则或 SQL。

**组件清单（理想状态）**

- **采集层**：定时爬虫（newspaper4k 或其后继）+ 内容哈希变更检测 + 限流抓取器。按学校/数据源配置驱动。
- **提取与物化**：受约束的 LLM 调用（结构化输出 + 校验重试），产出规范 `Notice` 与零或多条 `TodoItem`。待办在写入时一次性生成并共享；用户私有状态（已完成/已跳过/已延后）存于独立覆盖表。
- **存储**：
  - 关系型：PostgreSQL（通知、待办、用户画像、订阅、订单、审计日志、token 用量）。
  - 向量：同一 PostgreSQL 实例内的 pgvector（或专用向量扩展）。Chroma 被替换。
  - 对象存储（可选）：原始 HTML/PDF 快照，用于审计与重新提取。
- **检索**：混合检索（BM25 + 稠密嵌入 + RRF 融合，k=60）。查询时对过期通知施加时间衰减或硬排除。结构化过滤始终先走 SQL。
- **对话层**：单一 ReAct 智能体，可调用按智能体分组的小型工具注册表。工具是 FastAPI 端点的薄封装。无需 A2A 协议。
- **服务履约**：订单创建、状态跟踪、结算。按钮直接调用 API；自然语言意图经 tool calling 路由。三层审批（自动 / 通知后短窗取消 / 硬门控）在 API 层强制执行，而非 LLM 内。
- **服务商生态**：外部服务（跑腿、打印、教材、组队、就业）仅在真正出现多服务商市场时，通过薄 MCP 兼容适配器注册。此前直接 REST/SDK 集成即可。
- **前端**：正式 Web 应用（React/Next.js 或同等方案），支持实时更新（SSE 或 WebSocket），用于审批门控、状态与思考轨迹。Streamlit 退役。
- **可观测性**：token 计量、延迟直方图、分阶段成功率、结构化失败分类（工具/推理/幻觉/死循环/溢出/拒绝）。
- **部署**：容器化（单节点 Docker Compose，多租户 Kubernetes 或托管容器）。采集、提取、API、UI 分离环境。密钥与模型凭证在应用外管理。

**数据流（理想）**

1. 调度器触发已配置数据源的爬取。
2. 新页面或内容变更页面插入（或更新），状态为 `raw`。
3. 提取 worker 认领批次，执行受约束 LLM 提取，写入结构化字段与可选待办，更新状态，并 upsert 对应向量分块。
4. 用户查询（列表/筛选/搜索/对话）先走 SQL 结构化谓词，再走混合检索。
5. 待办列表为共享待办与用户私有状态的简单连接，按截止时间排序。
6. 服务动作在审批策略下创建持久订单；回调更新订单状态并回流推荐信号。

**协议**

- MCP 仅在阶段 3 及以后、外部服务商数量使 N×M 集成成本过高时才有用。A2A 不需要：系统保持单一逻辑应用与共享存储；stigmergy（数据库写入即通信）已足够。
- Tool calling 仅保留在 OpenAI 兼容 Agents SDK（或其后继）内，用于对话智能体。

**部署形态**

单机开发机 → Docker Compose（PostgreSQL + API + workers + UI）→ 托管云（Postgres + 容器平台 + 对象存储）。采集与提取 worker 可水平扩展，因管道已设计为增量处理。

**需升级或推翻的现有决策**

- Streamlit → 完整 SPA/前端框架。Streamlit 适合智能体仪表盘，但无法支撑带实时审批门控的多用户生产界面。
- Chroma → pgvector（或 PostgreSQL 内同等方案）。关系与向量同库可简化事务、删除与一致性。
- 本地嵌入模型 → API 嵌入服务（在成本与质量证明合理时切换）；本地模型保留为回退与离线评测。
- “不是多智能体系统”的定位仍然正确，应予保留。将确定性管道阶段强行 Agent 化属于纯粹过度工程。
- 批量、写入时待办生成仍然正确；数据源级开关亦正确。
- 三层审批与双通道（按钮 + tool）仍为理想方案。
- 混合检索、合理分块与时间衰减仍为必须升级项。

**Q2. 理想开发路径**

**阶段 0 – 当前状态（MVP 已完成）**  
目标：单用户、单学校闭环可用。  
交付物已存在。验收：黄金集提取准确率、带引用的基础 RAG 回答、Streamlit 界面可用。

**阶段 1 – 管道生产级硬化**  
目标：使数据平面可信且可观测。  
构建：内容哈希变更检测、删除/重提取时自动向量同步、token 计量与失败分类、Pre-flight token 长度检查、可配置并发上限与指数退避、混合检索 + 时间衰减、分块参数校准。  
学习目标：LLM 管道可靠性工程与检索质量度量。  
交付物：指标仪表盘、更新后的评测脚本、混合检索配置。  
验收：线上数据源提取成功率 >95%，RAG recall@5 可度量，删除后无孤立向量。  
进入下一阶段条件：每日爬取稳定两周。

**阶段 2 – 多用户基础**  
目标：身份、偏好与共享待办 + 私有状态。  
构建：FastAPI、PostgreSQL 迁移、认证、用户画像（身份/学院/专业/年级/标签）、关键词订阅、用户待办覆盖表、基础推送（站内 + 邮件或 Webhook）。  
学习目标：多租户数据建模与认证。  
交付物：登录、画像页、个性化待办列表与过滤后的通知流。  
验收：两名独立用户看到相同共享待办但各自完成状态独立；关键词订阅正确过滤。  
进入条件：schema 迁移干净、重载无数据丢失。

**阶段 3 – 对话式服务层**  
目标：用工具闭合“通知 → 行动”闭环。  
构建：按智能体分组的工具注册表（查订单状态、创建打印/跑腿订单、跳转报名链接、列出服务商）、带 SSE 事件流的三层审批 UI、订单持久化与状态回调。  
学习目标：工具设计、人机协同模式、幂等性。  
交付物：至少一种服务（打印或跑腿）的完整端到端订单。  
验收：按钮路径与对话路径产出相同持久订单；审批门控正确触发。  
进入条件：工具幂等且完整日志。

**阶段 4 – 多学校与配置成熟**  
目标：同一代码库服务多所院校。  
构建：学校级 YAML（或数据库驱动）配置、数据源优先级与 generate_todos 开关、学校作用域数据隔离或打标、数据源管理后台。  
学习目标：配置驱动系统与租户隔离。  
交付物：第二所学校无需改代码即可完整运行。  
验收：切换学校配置即可干净改变爬取目标、提取行为与界面标签。  
进入条件：阶段 1–3 指标在新学校仍成立。

**阶段 5 – 服务商生态与 MCP**  
目标：外部服务成为一等公民且可插拔。  
构建：服务商注册、结算账本、曝光/转化指标；仅在服务商数量真正需要时引入 MCP 适配器。  
学习目标：市场设计与协议演进。  
交付物：至少三家独立服务商上线；结算报表。  
验收：新服务商仅需配置 + 适配器即可接入。  
进入条件：订单量与失败率可度量。

**阶段 6 – 推荐、推送与打磨**  
目标：主动、偏好感知的界面。  
构建：规则匹配 + 可选嵌入相似度、每日截止扫描、更丰富推送渠道、日历导出、前端打磨（过程可视化、审批历史）。  
学习目标：可解释且低成本的推荐系统。  
交付物：个性化首页与可靠截止提醒。  
验收：待办完成率或通知参与度有可度量提升。  
进入条件：已有足够行为数据用于评估。

**阶段 7 – 运维卓越**  
目标：生产就绪。  
构建：完整可观测性、成本预算、自动化评测回归、灾难恢复、文档、安全审查。  
学习目标：运行 LLM 支撑服务的生产实践。  
交付物：运行手册、SLO、成本仪表盘。  
验收：系统可由原作者以外的人员独立运维一周。

**Q3. 阶段排序逻辑**

顺序遵循依赖与风险：

- 管道可靠性（阶段 1）是基础；后续所有功能均建立其上。不可跳过。
- 多用户身份（阶段 2）必须先于个性化与服务订单。离开单用户后不可跳过。
- 服务工具与审批（阶段 3）兑现核心产品差异化。对既定愿景不可跳过。
- 多学校（阶段 4）在配置模型稳定后可与阶段 3 部分并行，但优先级低于单学校闭环。
- 服务商市场（阶段 5）仅在订单存在且量级出现后才有价值；在真实外部伙伴出现前为可选。
- 推荐与打磨（阶段 6）在核心闭环成立后杠杆高，但次要。
- 运维卓越（阶段 7）从阶段 1 后持续，正式收尾于最后。

配置工作与工具/审批工作在 schema 稳定后可并行。MCP 在服务商数量使直接集成成本过高前属纯可选加成。

**Q4. 需确认事项**

阶段 1 前：度量真实 token 成本与完整一周线上爬取的提取失败率。方法：对每次 LLM 调用埋点，记录输入/输出 token 与延迟；运行黄金集 + 50 条新通知。信号：每条通知成本与失败模式已量化。

阶段 2 前：确认“共享待办 + 私有状态”是正确的多用户模型。方法：纸面原型或对 5–10 名目标用户做简单调研（“希望个人待办还是校园共享待办列表？”）。信号：明确多数偏好。

阶段 3 前：验证至少一种服务（打印或跑腿）的需求。方法：落地页或应用内“我愿意使用”按钮 + 定性访谈。信号：≥30% 受访学生表达意愿，或真实伙伴愿意对接。

阶段 4 前：确认第二所学校通知结构足够相似。方法：手动爬取并提取该校 20 条通知。信号：提取准确率无需大幅改 prompt 仍保持阶段 1 阈值以上。

阶段 5 前：度量订单量与服务商兴趣。方法：运行阶段 3 一段时间并统计完成订单；与校内服务经营者沟通。信号：持续订单与至少一家外部伙伴准备对接。

阶段 6 前：确认规则匹配已不足。方法：对保留用户行为做规则 vs. 嵌入相似度的 A/B 或离线评估。信号：可度量提升足以证明额外复杂度合理。

**Q5. 技术选型理由**

- **OpenAI Agents SDK**：提供受约束输出、tool calling 与智能体循环，可对接任意 OpenAI 兼容端点。作为唯一对话运行时。仅在 SDK 成为硬约束或出现同等可靠的更优开源替代时切换。失败场景：对智能体抽象的厂商锁定。替代：纯 LangGraph 或自研 ReAct 循环。
- **SQLite → PostgreSQL**：SQLite 适合单用户 MVP；PostgreSQL 提供并发、全文检索与同库 pgvector。在多用户工作开始时切换。失败场景：过早迁移成本。替代：若并发长期较低可继续谨慎使用 SQLite。
- **Chroma → pgvector**：消除双库一致性问题。在阶段 1 或 2 切换。失败场景：超大规模向量性能（校园通知场景极不可能）。替代：仅在量级爆炸时再引入专用向量服务。
- **本地嵌入 → API 嵌入**：本地模型免费且可离线；API 模型通常检索质量更好、运维更简单。在评测显示明确质量收益且成本可接受时切换。失败场景：API 成本突然飙升。替代：永远保留本地模型用于评测与低流量部署。
- **Streamlit → React/Next.js（或同等）**：Streamlit 适合内部仪表盘；带实时门控的多用户生产体验需要正式前端。在阶段 2/3 边界切换。失败场景：低估前端工作量。替代：Gradio 或继续重度定制 Streamlit（长期不推荐）。
- **newspaper4k**：务实，对当前学校站点有效。保持默认爬虫直至某站点破坏启发式。失败场景：非标准页面提取脆弱。替代：按数据源定制 BeautifulSoup/Playwright 爬虫，或更稳健的商业爬虫。
- **批量 LLM 处理**：摊销固定 prompt 成本并支持增量处理。成本控制核心。失败场景：突发爬取导致队列积压。替代：纯按需（更贵、延迟更高）。
- **FastAPI**：干净的异步 HTTP 层、自动 OpenAPI、易封装工具。从阶段 2 起成为唯一后端表面。失败场景：过早微服务化。替代：比感觉必要的时间更长地继续纯 Streamlit + 脚本。
- **任务队列（Celery / ARQ 等）**：当爬取、提取与订单处理必须在进程重启后存活并独立扩展时必需。随多用户或重度批处理引入。失败场景：消息代理运维复杂度。替代：在进程内 asyncio 队列上坚持更久。

**Q6. 额外问题**

**a. “完成”的定义。**  
基于里程碑：（1）管道可靠性与可观测性闭环，（2）多用户身份与共享/私有待办上线，（3）至少一种服务在三层审批下完整闭环，（4）第二所学校仅靠配置即可运行，（5）个性化带来可度量参与度提升，（6）系统可由原作者以外的人员按文档与成本控制运维。当产品可交由小型校园试点团队且原作者不再是单点故障时，即为“完成”。

**b. 最大失败风险（唱反调）。**

1. 服务层从未获得真实伙伴或真实订单；产品停留于精致的通知阅读器。
2. 新学校或新通知格式上提取质量下降速度快于评测框架的检测能力，侵蚀信任。
3. Token 与基础设施成本增长快于用户价值，使项目变成昂贵爱好。
4. （附加）在确定性管道与单一闭环服务尚未稳固前，过度投入多智能体或 MCP 抽象。

**c. 最不可跳过的阶段。**  
阶段 1 – 管道生产级硬化。没有可信、可观测、一致的数据，后续一切建于沙上。若只能深入做一个阶段，先把数据平面做扎实。

**d. 最易过度工程的部分。**  
将整个系统变成“真正多智能体系统”或过早引入 MCP/A2A 的冲动。对照您已有决策清单：您已正确拒绝过早多智能体设计并推迟 MCP。同一纪律须应用于推荐复杂度、记忆图谱与复杂监督拓扑。管道 + 路由 + 单一 ReAct 智能体已是正确形态。

**e. 对“边学边做”开发者最有迁移价值的三个技术点。**

1. 受约束结构化提取 + 校验重试 + 黄金集评测。
2. 混合检索设计，以及在增加复杂度前先度量召回/精确率的纪律。
3. 双通道行动设计（确定性 UI + tool calling）与明确人机协同审批层级。

**Q7. 独立建议 – 您可能遗漏的三件最重要事项**

1. **首次试点后的运维所有权。**  
   您已仔细设计了快乐路径，但尚未设计谁接收凌晨两点的爬取失败告警、如何强制执行成本预算、以及如何让第二位维护者上手。一旦系统离开您的笔记本，这些就成为现实问题。

2. **第二所学校的冷启动与数据引导策略。**  
   配置必要但不充分。您需要可重复的流程来发现数据源、播种黄金集、并在承诺多学校支持前度量新域上的提取质量。

3. **明确的、非技术的产品成功指标。**  
   提取准确率与 RAG 相关性必要但不足。定义您愿意接受的、证明产品有价值的行为结果（待办完成率、服务订单转化、用户报告的错过截止减少）。没有这些，理想架构仍是工程练习而非产品。

理想终态可达，且您现有架构直觉大体正确。保持“提示链 + 路由 + ReAct”核心，先硬化数据平面，再开放服务与多租户层。该顺序可同时最大化学习收益与最终系统被真正使用的概率。
