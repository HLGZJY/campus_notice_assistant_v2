## 3. 模块依赖关系（已核实）

### 3.1 依赖方向（均为单向）

```
pages/  (Streamlit, 纯前端)
   │  只 import services（无 core/storage/utils 直接 import，除订阅页一处 get_connection 例外）
   ▼
services/  (业务编排：9 个服务，薄封装，全部同步函数)
   │  import core / storage / config / crawler / utils
   ▼
core/  (LLM Agent：extractor/todo/qa/date_utils/models) ──┐
storage/  (db.py SQLite / vectorstore.py Chroma / hybrid.py / models.py) │
crawler/  (base.py newspaper4k / web_crawler.py)                         │
config/   (schema.py/store.py/defaults.py)                               │
utils/    (llm.py / embedding.py) ◄── core 依赖 utils.llm                  │
   ▲                                                                    │
   └────── 全部依赖 ConfigStore（config/store.py 单例）◄─────────────────┘
```

### 3.2 关键依赖点

- `utils/llm.py:run_agent`：**唯一的 LLM 调用点**（提取/待办/问答共用）+ token 计量，已集中。
- `utils/embedding.py`：唯一的 embedding 调用点（本地模型 + OpenAI-compatible 两路）。
- `services/notice_service.py`：爬取/提取编排中枢，被 scheduler、pages/1、extract.py、admin_service 复用。
- `services/admin_service.py` → 复用 `notice_service.extract_notice`、`qa_service.rebuild_index`。
- `scheduler.py` → 复用 `notice_service.crawl_all_sources/extract_batch`、`reminder_service.scan_reminders`。
- `crawler/web_crawler.py` 与 `services/notice_service.py` 都会调用 `subscription_service.match_notice`（抓取后/提取后增量维护命中）。
- 唯一的直接耦合瑕疵：`pages/5_🔔_订阅管理.py:21` `from storage.db import get_connection`（只读 count，可收编进服务）。

## 5. 前后端分离前置分析（重构准备工作）

### 5.1 现状结论：后端已基本是"API 就绪"形态

- `services/` 是**事实上的业务后端**：所有页面行为（查询/写库/LLM/爬取/配置）都走 services，返回 dict/模型对象。
- 页面只负责「拿数据→渲染→回传意图」，未直接在页面里写业务 SQL（仅订阅页一处 count 例外）。
- `scheduler.py` 已是独立进程，与 UI 解耦 —— 未来可直接变成后端常驻服务的一部分。
- Streamlit 的 `session_state` 只用于页面内交互状态（两步式、埋点去重、编辑中表单），**不承载业务状态**，拆分时无状态迁移负担。

### 5.2 拆分需要解决的边界问题

| # | 现状耦合 | 拆分动作 |
|---|---|---|
| 1 | services 返回 **dict/sqlite3.Row/Pydantic 对象**混用 | 定义统一 **API 契约模型**（pydantic response schema），services 层之上加薄 HTTP 层（FastAPI） |
| 2 | 长时操作（爬取/提取/问答）为**同步阻塞** | 拆分后需异步任务化（BackgroundTasks/任务表/SSE 流式问答）；Streamlit 靠 spinner+rerun 掩盖了这点 |
| 3 | `core/qa.py` 依赖 `storage/vectorstore` 的 **langchain Document** 类型 | HTTP 层需把 Document → 可序列化 dict（`as_source` 转换），前后端契约不受 langchain 污染 |
| 4 | 配置读写**直接落 YAML 文件**（ConfigStore 单例） | 后端进程内单例可保留；若前后端分离部署，需增加「配置 API」且注意多进程 YAML 写入竞态（现有 .bak 备份机制需评估并发） |
| 5 | 埋点写入位置在 pages 内（`track_event`） | 移动端/Web 前端调 `POST /api/events`，埋点逻辑留在后端 services |
| 6 | 两步式交互（`ui/two_step.py`）强依赖 Streamlit session_state | 语义可平移为「后端请求-确认-执行」三个 API（POST preview / POST confirm），前端用路由状态替代 session_state |
| 7 | `utils/llm.py` / `utils/embedding.py` 为**进程级单例**（模型加载缓存） | 后端进程常驻后单例自然成立；注意 embedding 模型内存占用只加载一次 |
| 8 | 页面筛选参数直接透传 services（status/source/type/keyword/is_action/limit） | 平移为查询字符串参数即可，契约已清晰 |

### 5.7 services 返回值序列化核实（小件 3 完成）

- 结论：**services 边界返回值均为 dict / list[dict] / 标量**，无 `sqlite3.Row` 泄漏。
- 核实点（`dict(r)` 统一在服务内完成）：
  - `notice_service.get_notices:139` `[dict(r) for r in rows]`
  - `notice_service.get_notice_detail:151` `dict(row)` + key_dates 解析
  - `qa_service.rebuild_index:75` `[dict(r) for r in rows]`
  - `todo_service.get_todo_stats:57` `{r["status"]: r["n"]}` 已折叠为标量
  - `subscription_service.preview_subscription_matches:113-114` `matches_subscription(dict(r), sub)`
  - `reminder_service._scan_*:62-73` 行内索引 `r["deadline"]`，仅用于内部统计，不外泄
  - `storage/db.py:get_todos:478` / `get_reminders:565` 底层已 `[dict(r) for r in rows]`
- 推论：FastAPI 层只需声明 pydantic response schema，**不需要额外转换器**；`core/qa.py` 的 `QAResult` 是唯一例外（§5.2-3，HTTP 层做 `as_source` 序列化）。

### 5.8 config/app.yaml 写路径并发语义（小件 4 完成）

- 写入实现：`config/store.py:_backup_and_write:257`，三步原子化：
  1. 写 `app.yaml.tmp`
  2. 旧文件复制为 `app.yaml.bak`
  3. `os.replace(tmp, app.yaml)`（同目录原子替换）
- **单进程内**：`ConfigStore` 为进程级单例（`get_instance`），写操作串行，`.tmp/.bak/os.replace` 保证断电/异常不产生半文件；UI 保存采用二次确认 + 重启/重载生效（`force_reload_config`）。
- **多进程（拆分后风险）**：若调度器与 API 服务各自持有单例同时写 `app.yaml`，`os.replace` 保证文件不损坏，但**最后写入者胜出、另一进程内存态失真**（双单例内存与磁盘漂移）。
- 拆分后约定：`app.yaml` 写入权**唯一归后端 API 进程**；调度器/CLI 只读（`force_reload` 后重新加载）。若需多写者，应在配置层加文件锁（如 `msvcrt`/`filelock`）后再进入 `_backup_and_write`。
