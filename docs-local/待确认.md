**Q0-3 Token 成本核算**

- 背景：token 即成本，一次批量提取 = 通知数 × 单条提取 token；批处理会放大成本，所以"增量处理"（只处理新通知）是核心省钱手段。
- 落点：采集管道已设计为"仅新通知调 LLM"；问答按需调用。需建立 token 计量（见 Q6-4）。
- 待确认：是否接受"批处理+增量"模式，还是保持现在的按需触发？
- ✅ 已确认（2026-08-09）：接受"批处理+增量"。**token 消耗详解**（留档）：
  - 消耗点 = 每条通知 1 次（或多次）LLM 调用，每次调用 = input + output
  - input-系统部分：提取指令 + 输出格式定义（固定，~300 token）
  - input-正文部分：标题 + raw_content（**主导因素**，中文约 1-2 字/token，1000 字 ≈ 600-1000 token）
  - output：结构化 JSON（类型/截止/地点/key_dates/摘要，~200-500 token）
  - 重试：校验失败回传错误再调（M2 最多 2 次），每次重试 = 重新付 input+output
  - 批量总消耗 = Σ每条（input+output）×（1+重试率）
  - 影响因素排序：通知条数（线性）> 正文长度（最大可变项）> 重试率 > 输出规模 > 待办生成（M3 另一次小调用）
  - 示例：27 条 × 平均 1500 字（≈1000 token）× 重试率 10% ≈ 50K token/轮；首次全量贵一次，之后增量每轮只有新通知的量
  - 结论：按需触发是"每条被点开都付钱"，批量是"每条只付一次"，且需建 token 计量（见 Q6-4）

## 第4章 Agent 范式与多 Agent 架构

**Q4-3 Agent 间通信与状态**

- 背景：长期记忆可以用关系表（结构化，可查询可统计），向量记忆用于语义召回；不必一律上向量库。
- 落点：画像、行为用关系表；偏好匹配用 tag 精确匹配；不需要"记忆向量库"。
- 待确认：确认不引入记忆专用向量库？

## 第6章 Harness 工程化

**Q6-1 定时调度**

- 背景：APScheduler/cron 单机足够；需配置抓取频率、提取频率、过期清理频率。
- 落点：ROADMAP P1 已列 APScheduler；采集=1h、提取随采集、清理=每日。
- 待确认：确认调度频率与工具选型（APScheduler）？

**Q6-2 增量与去重强化**

- 背景：URL UNIQUE 只防重复插入，不防"同一页面内容更新"（标题变了、公告改了）。
- 落点：需加"内容指纹"（哈希正文）检测已抓 URL 的更新 → 触发重新提取+向量更新。
- 待确认：确认加入内容变更检测？

**Q6-3 批量并发与限流**

- 背景：批量 LLM 调用要控制并发（防止限流），失败指数退避重试。
- 落点：M2 已有指数退避（继承自 RAG 项目）；批量需加并发上限（如 4-8 并发）。
- 待确认：确认并发控制写入需求？

**Q6-4 可观测性**

- 背景：监控四件套——token 消耗、响应时间、成功率、失败日志；trace/span/log。
- 落点：现有 crawl_log 只有抓取日志；缺 token 计量表、提取/问答失败统计。
- 待确认：确认加"token 计量与失败统计"（服务商后台也要曝光/转化统计）？

**Q6-5 任务队列必要性**

- 背景：单机单进程先不引 Kafka/Redis Stream；进程内队列（ThreadPool/队列）即可；多用户阶段再上 FastAPI+异步任务。
- 落点：与 Q4-3 同源。
- 待确认：合并确认。

## 第7章 数据架构

**Q7-1 待办批处理管道（含数据源开关）**

## 第8章 推荐与推送

**Q8-1 推送渠道与触发**

- 背景：推送 = 离线匹配索引 + 定时扫描 + 渠道分发（站内信/Webhook/第三方）；事件驱动可选。
- 落点：单机阶段：站内推送（待办中心/首页红点）+ 临近截止提醒（每日扫描）。
- 待确认：确认单机阶段只做站内推送？外部渠道（微信/邮件）留阶段2？

**Q8-2 匹配规则设计**

- 背景：tag 对 tag 精确匹配 + 规则粗排（时效/类型/优先级），可解释、零成本。
- 落点：通知 tag（notice_type/source/关键词）+ 用户 tag（身份/专业/订阅词）→ 匹配表 + 排序规则。
- 待确认：确认规则引擎为主、LLM 只做通知打标（已有）？
- 🔍 指南补充（ch23 Agent Router / ch16 路由）：推送匹配可选升级——用户 tag 与通知 tag 分别 embedding，用余弦相似度做语义匹配（ch23 能力路由思路，无需硬编码规则表），作为 P2 可选项，替代/补充精确匹配。

**Q8-3 LLM 精排**

- 背景：推荐精排可选 LLM，但成本高、延迟大；数据量大前规则粗排足够。
- 落点：P2 再评估；需求文档标注"可选"。
- 待确认：确认精排仅作为 P2 可选项？
