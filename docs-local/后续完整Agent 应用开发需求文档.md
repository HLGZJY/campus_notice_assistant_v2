# Agent应用开发需求文档

## 1 文档基础信息

1.1 项目名称：AI校园事务智能助手
1.2 产品定位：面向高校师生的多角色AI智能Agent，一站式处理校园通知、事务办理、生活服务全流程需求
1.3 使用人群：在校本科生、研究生、高校教师、学校行政工作人员、校园线下服务商
1.4 开发目标：依托AI智能体能力，实现校园通知自动识别、事务待办生成、校园服务一键匹配，打通“看通知-办事情”完整闭环

## 2 核心业务需求概述

现有校园信息分散在十余个渠道，用户仅能查看通知，无法直接联动对应办事服务；本项目通过AI Agent作为核心大脑，自动抓取、解析校园公告，识别隐藏事务需求，主动为用户生成待办清单，并自动匹配校内跑腿、打印、竞赛组队、就业等配套服务，无需用户手动切换多个工具。

## 3 用户角色与核心诉求

### 3.1 学生Agent服务对象

1. 自动汇总全校所有学院、教务处、团委、就业中心通知，无需手动多渠道查看
2. AI自动识别通知内办事需求（报名、盖章、材料打印、竞赛组队、校招等）
3. 自动生成结构化待办，标注截止时间、所需材料、办理地点
4. 一键发起跑腿代办、线上文印、二手教材交易、组队招募
5. 根据年级、专业、兴趣自动推送匹配公告与活动

隐藏要求：

1. 自动汇总通知范围，是否需要根据学生背景做范围圈定？
2. 通知如何保持为最新的，在rag之前是否需要逐个检查通知渠道，或是只检查与学生专业相关的渠道，按照相关顺序
3. 数据库怎么做？要不要把每个来源隔开？我们应有的数据架构是怎么样的，怎么针对设计？
4. 自动生成待办需求，这一步是发生在哪里？学生通过rag检索通知出来结果之后吗？不可能每一个同学问一次就生成一次吧？是不是得复用第一个人的
5. 事件发起在哪个环节生效？生效方式是什么？给入口还是给什么？那些事件作为tool——calling吗？
6. 这些事件是否需要分别做一个动态的rag
7. 自动推送和匹配是怎么做到的？怎么做才是效率最高的，这是否需要AI参与

### 3.2 教师Agent服务对象

1. 自动过滤科研、教务、学术会议相关通知，屏蔽无关信息
2. 历史公告一键检索回溯
3. 科研申报、学术活动自动生成待办提醒

待确认要求：
历史公告检索回溯具体是什么？是相关联的公告要生成时间线给它串起来吗？

### 3.3 行政人员Agent服务对象

1. 发布通知后，AI自动统计学生待办查看、办理进度
2. 汇总高频咨询问题，生成统一答疑内容

### 3.4 校园服务商（打印店/跑腿团队/书商）

1. AI Agent分发精准校园订单流量
2. 线上接单、订单状态同步、交易结算

## 4 AI智能Agent核心基础能力（核心模块）

### 4.1 信息采集智能Agent（基础引流模块）

1. 自动定时抓取校内的信息渠道公告内容，实时更新
2. 对所有公告统一分类、去重、关键词标记
3. 支持用户自定义关键词订阅，有匹配通知主动推送

### 4.2 校园事务识别AI Agent（核心大脑）

1. 读取原始校园通知文本，自动生成精简摘要
2. 识别通知包含的事务类型：报名、盖章、打印、竞赛、就业、学术申报等
3. 自动拆解事务关键信息：截止日期、办理地点、材料清单、操作步骤
4. 将纯文本公告转化为标准化待办任务卡片
5. 根据用户身份（学生/教师）过滤无关事务

### 4.3 事务闭环服务调度Agent（价值核心）

接收识别Agent输出的待办任务，自动匹配对应校园服务，提供一站式办理入口：

1. 跑腿代办服务：文件领取、材料上交、盖章代办下单
2. 线上文印服务：文件上传、在线支付、配送至宿舍
3. 二手教材交易：教材发布、检索、撮合交易
4. 竞赛组队服务：自动匹配同赛事队友，搭建交流小组
5. 校招就业服务：宣讲会提醒、简历指导、岗位推送

### 4.4 个性化推荐Agent

1. 记录用户阅读、收藏、下单、搜索行为数据
2. 区分学生、教师、行政三类身份，千人千态推送通知与服务
3. 过滤冗余信息，降低信息干扰

## 5 前端应用基础功能需求（用户交互层）

### 5.1 首页总览

1. 统一消息聚合列表：展示全部校内最新通知
2. AI生成今日待办事务置顶展示
3. 高频服务快捷入口：跑腿、打印、二手、组队

### 5.2 通知详情页

1. AI自动生成公告精简摘要
2. 页面下方展示AI识别生成的待办卡片
3. 卡片附带对应服务一键办理按钮

### 5.3 待办中心

1. 所有AI识别生成的事务统一管理
2. 按截止时间排序，临近到期自动提醒
3. 标记已完成/未完成事务

### 5.4 校园服务市场

展示全部接入服务商，由调度Agent根据用户待办自动推荐对应服务

### 5.5 个人中心

1. 身份设置：本科生/研究生/教师/行政人员
2. 关键词订阅管理
3. 订单记录、交易账单
4. 消息推送开关

## 6 服务商后台配套Agent能力

1. 订单智能分发Agent：根据用户地理位置、需求自动分配服务商
2. 交易结算Agent：自动计算平台抽成，生成对账数据
3. 流量统计Agent：统计平台曝光、订单转化数据

## 7 核心业务流程（Agent协同逻辑）

1. 采集Agent定时抓取全校公告
2. 事务识别Agent解析公告，生成待办任务
3. 推荐Agent根据用户身份、行为过滤、排序内容
4. 用户查看通知，点击待办卡片
5. 服务调度Agent匹配对应服务商，生成订单
6. 交易完成后，数据回流推荐Agent，优化后续推送精度

## 8 基础非功能需求

1. 多角色适配：一套Agent系统同时满足学生、教师、行政、服务商使用
2. 自动化闭环：从通知读取到服务完成全程AI驱动，减少人工操作
3. 轻量化交互：无需复杂操作，打开应用即可查看AI整理好的内容与待办
4. 数据合规：用户信息、校园公告数据加密存储，仅用于校内服务

## 9 项目分阶段功能雏形规划

### 阶段1（最小可用雏形MVP）

仅实现两大核心Agent：信息采集Agent + 事务识别Agent
功能：公告统一聚合、AI摘要、自动生成待办提醒；暂不接入线下交易服务

### 阶段2（完整闭环版本）

新增服务调度Agent，接入跑腿、文印线上交易能力，实现通知到下单全流程

### 阶段3（生态拓展版本）

新增二手交易、竞赛组队、就业服务模块，完善服务商后台Agent能力

## 10 核心差异化需求（Agent产品亮点）

市面同类产品仅做信息聚合或单独生活服务；本产品依靠多智能体协同，**唯一实现“通知AI识别+事务待办+校内服务联动”一体化**，AI作为中间调度核心，自动串联信息与线下办事场景，解决校园事务“最后一公里”痛点。

## 11 架构与Agent设计确认（对照《智能体AI漫游指南》审计，2026-08-09）

> 本节为架构层面的最终确认结论，与 `docs/待确认.md` 第10章审计表配套。

### 11.1 总体形态：不是真多Agent系统

经审计确认，本文档中的“信息采集Agent / 服务调度Agent / 推荐Agent”大部分为**确定性组件**（爬虫、规则引擎、SQL），仅事务识别与问答是 LLM 节点。真实技术形态为：

- **Prompt 链数据管道**（采集→提取→待办→推送，步骤固定可预测，环节间设质量门）
- **路由**（对话意图分派：查通知→问答 Agent；办事项→事务 Agent）
- **ReAct 问答**（唯一自主 Agent 环节）

理由：指南 ch19 反模式“过早Agent化”——能解决问题的 Prompt 链永远胜过“也许能解决”的多Agent系统。文档后续修订中，采集/调度/推荐宜称“模块/管道节点”，避免过度设计。

### 11.2 拓扑与协同（ch24）

- 拓扑：**Pipeline**（顺序处理、阶段依赖清晰、可调试性高）；不引入 Supervisor 总控（<5 Agent 用集中式最简单的规则下也不需要）
- Agent 间协调：**Stigmergy**——通过共享数据库（SQLite 状态表）写入即通信，无需消息队列/A2A（单机同构系统）
- 多用户阶段（阶段2+）：FastAPI + 异步任务队列（Celery 模式，ch25 异步执行是常态），检查点/续跑支持断点恢复

### 11.3 事件与服务接入协议（ch19/21）

- 阶段2：**工具注册表 + 按 Agent 分组**（OpenAI Agents SDK 原生 tool，5-6 个工具全量注册无上下文压力）；按钮直连 API + 对话 tool calling 双通道；工具签名五要素（名称/描述/参数/输出/约束）
- 阶段3：服务商生态接入升级 **MCP**（N×M→N+M 化简；annotations 标注 readOnly/destructive/idempotent 支撑审批自动分级）
- **A2A 不需要**（ch23：横向协议用于异构 Agent 网络，本项目单校内同构）
- 审批门控：**三层制**（ch26）——Tier1 自动批准（只读操作）、Tier2 通知+短窗口取消（中风险）、Tier3 阻断门控（支付/不可逆操作）；判据五问：可逆性/影响范围/置信度/成本/新颖性

### 11.4 RAG 体系确认（ch16）

- 检索：结构化条件走 SQL（类型/来源/deadline），语义检索走向量；P1 升级**混合检索 BM25+稠密+RRF**（k=60 排名融合）
- 分块：256-512 token、重叠 10-15%（事实问答+摘要混合场景）
- 索引：增量 upsert（按通知 ID 替换）、TTL 过期清理（截止日已过）、删除/重提取自动同步向量
- 时效性：过期通知降权/排除（时间衰减检索公式）

### 11.5 记忆与 Harness（ch17/18）

- 记忆四分类落地：工作记忆（对话上下文）+ 情景记忆（Chroma）+ 语义记忆（SQLite 结构化）；程序记忆（工具技能）阶段2 具备；MemGPT/知识图谱不需要
- Harness：上下文预算公式 + Pre-flight token 检查（提取管道最需要）+ 历史滑动窗口压缩（问答多轮，P1）+ 循环检测/最大迭代守卫（阶段2 tool calling 必需）+ 六类失败分类法（Tool/推理/幻觉/死循环/溢出/拒绝）
- 状态四层：对话/任务（游标与 checkpoint）/Agent（当前计划）/持久化（画像与行为）

### 11.6 评测体系（ch14）

- 提取/待办：黄金集字段对比（执行式评估，已落地）
- 问答：LLM-as-Judge（κ>0.6 且一致率>80% 校验、交换增强防偏置）
- RAG 三层评估：检索（Recall/Precision/MRR）→ 生成（忠实度）→ 端到端（RAGAs 免参考框架）
- 模型选型基准评测见 GitHub issue #2

### 11.7 前端演进（ch26）

- 阶段1：Streamlit 定位为 Agent 仪表盘（指南确认其适用场景），继续沿用
- 阶段2：增加“过程可视化 + 审批门控”——SSE 类型化事件（status/thinking/tool_call/approval_required）、工具来源可视化、撤销路径，遵循“透明协作者”原则（自动化偏差防护）
